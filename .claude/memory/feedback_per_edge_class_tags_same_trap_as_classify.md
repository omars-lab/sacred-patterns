When two `polygon` declarations share an edge in bikar DSL, applying class tags via the per-edge syntax `edges from polygon_A .classA` + `edges from polygon_B .classB` does NOT produce two adjacent faces with distinct face_classes. Instead, the face-walker emits ONE absorbed face whose `face_class` attribute carries BOTH tags as a space-separated string (e.g., `class="square scalene_tri"`), and qiyas's gt-emitter then mis-types it (e.g., `type=pentagon` because the polyclass face_class string doesn't match any single-class polygon classifier).

**Why:** the qiyas#132 Tick 20 entry (scalene-square-quad-lens-mixed, 2026-05-26) was designed to sidestep the Tick 9 classify-by-`sides==N` trap by using per-edge class tags (`edges from square_poly .square`) instead of `classify .square where sides == 4`. The reasoning was that Tick 18's lens entry validated this alternative pattern. But the lens-class-tag case worked because the lens was DISJOINT from the polygon — no shared edges meant no shared per-edge tags. Tick 20 shares the C0.cpt0→C0.cpt1 edge between `polygon square_poly` and `polygon scalene_tri_poly`; that shared edge carries the `.square` tag from `edges from square_poly .square`, and bikar's face-walker treats it as belonging to the polygon ring that wins the half-edge walk — producing one face with the polyclass tag set, NOT two adjacent faces (the geometric truth). The Tick 17 face-walker arc-absorption pattern is the orthogonal version of this same bug: shared edges with conflicting source attribution produce absorbed faces.

The Tick 18 "alternative pattern" carries an implicit precondition that was never named: **per-edge class tags only escape the polyclass trap when the tagged primitives are topologically disjoint.** Once they share even one edge, the trap reasserts at the face-walker layer instead of the classify-by-predicate layer.

**How to apply:** when authoring a Tier 1 corpus entry that combines two same-class-eligible primitives (e.g., two 4-sided polygons that would both match `sides==4`) AND any topological coupling (shared-edge, shared-vertex with shared-edge fallback paths), do NOT reach for `edges from polygon_X .className` as the Tick-9-escape mechanism. The escape mechanism only works when the primitives are disjoint. Instead either (a) reframe the witness with heterogeneous sides counts (avoid the same-N collision entirely — e.g., replace one 4-sided polygon with a 5-sided irregular pentagon), (b) accept that the witness needs a DSL extension (classify-by-source-primitive), or (c) document the witness as polyclass-aware and write the contract check accordingly. Before authoring a same-sides Tier 1 composition, ALWAYS author a Tier 0 single-primitive test first to confirm the class-tag mechanism produces the expected face_class string in isolation, then verify it survives the topological coupling — Tier 17 (prove the primitive first) requires the isolated witness BEFORE the composite contract.

Together these establish: bikar's face-walker has a recurring class-attribution-on-shared-edges failure mode, manifesting differently per primitive type (arc-vs-polygon, polygon-vs-polygon, classify-vs-tag), but the underlying bug is one. **Sacred-patterns Tenet 17 (prove the primitive before composing) applies — author the Tier 0 single-primitive class-tag witness first.**
