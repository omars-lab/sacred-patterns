When TWO regular inscribed polygons share a single C0 (geometrically inscribed in the same circle) but have DISJOINT vertex sets (no shared topological vertex via construction), bikar's face-walker correctly subdivides them along their edge crossings — but the resulting sub-faces ALL inherit cross-class source_primitives (both `.square` AND `.triangle` tags, both `square_poly` AND `triangle_poly` polygon references). Since the classify DSL evaluates `sides==N` predicates against the SUB-face's actual side count (not the contributing polygon's intended class), AND the polyclass trap (Tick 9) prevents clean per-tag emission, every sub-face ends up with `face_class=None`. **Cross-polygon overlap topology cannot be cleanly classified using bikar's current `classify .name where sides==N` predicate DSL** — needs either a topological predicate (`source_primitives.contains('square_poly') and not source_primitives.contains('triangle_poly')`) or a "winding-number-based" face_class assignment, neither of which bikar currently supports.

**Why:** qiyas#132 Tick 76 (2026-05-27) authored `square-and-triangle-shared-circle.bkr.tmpl`. Construction: C0 at origin r=100, ÷24; square at indices [0,6,12,18] (axis-aligned, 90° steps); triangle at indices [1,9,17] (15° rotation, 120° steps). Disjoint vertex sets confirmed. Naive geometric prediction: 4 square-corner wedges + 3 triangle-corner wedges + 1 central kite overlap = 8 face shapes + 1 C0 circle = 9 shapes. **ACTUAL: 7 shapes (6 face shapes + 1 C0)**, ALL face shapes have `face_class=None`. Every face's source_primitives includes BOTH `.square` AND `.triangle` tags. Example: shape[0] = `[.square×3, .triangle×1, square_poly×2, triangle_poly×1]`; shapes[1-5] = mixed `[.square + .triangle]` tags in different proportions. The shape-count drift from 8 → 6 face shapes likely involves Tick 60 same-class union merging adjacent wedges with identical source-tag multisets, OR the face-walker collapses the kite-corner topology at edge crossings — not separately diagnosed.

The PASS criterion ("both polygon outlines recoverable from emitted source_primitives") IS met — every emitted face's source_primitives preserves at least one of `square_poly` / `triangle_poly` and the FULL list of references across all shapes covers both. So the **construction provenance survives** even though **the classify-DSL-driven face_class assignment is destroyed**. This confirms the local-arc-enrollment rule's behavior on shared-C0 generalizes from "1-N lenses + 1 polygon" (Ticks 69-74 PASS) to "2 polygons" but ONLY at the source_primitives layer — not at the face_class layer.

**Rule boundary refined:**
- **Cross-PRIMITIVE-TYPE on shared C0** (polygon + lens, Ticks 69-74): PASS for both source_primitives AND face_class.
- **Cross-POLYGON on shared C0** (this Tick 76): PASS for source_primitives, FAIL for face_class because polyclass trap fires when edge crossings split each polygon into sub-faces whose boundaries necessarily include edges of the other polygon.

**How to apply:** When authoring Tier 1 composites that pair two inscribed regular polygons on a single C0: (a) do NOT predict clean per-polygon face_class — predict `face_class=None` for ALL sub-faces, and design the witness so the PASS criterion lives at the source_primitives layer (not face_class); (b) if the downstream consumer (detector calibration, hierarchical diff) NEEDS clean per-polygon class disambiguation at the gt.json layer, you have three options — i) author each polygon as a SEPARATE blueprint+pattern + composite at the SVG/PNG layer (heavy), ii) wait until bikar's DSL gains a topological-predicate classify (`sources contains 'square_poly' xor sources contains 'triangle_poly'` — would need an `xor`/`exclusive` keyword), iii) accept the polyclass face_class=None outcome and have qiyas's detector re-derive polygon membership from the source_primitives multiset; (c) the same hazard fires for ANY two-or-more polygon composition on shared C0 regardless of D_n symmetry, because the edge-crossing mechanism is purely geometric — it doesn't depend on polygon order or rotation; (d) WHEN this is the desired witness (probing polyclass behavior on cross-polygon overlap), the entry SHOULD remain in the corpus as a NEGATIVE witness — useful for detector calibration on degenerate polygon-overlap topologies and as a regression marker for any future bikar DSL extension that lets classify rules use topological predicates instead of just `sides==N`.
