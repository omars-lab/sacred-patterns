When TWO lenses share a single DCEL vertex P with all four incident arc half-edges (degree-4 all-arc topology), the face-walker emits the correct shape count and correct face topology — but if the two non-shared circles are *ext-tangent at P* (centers colinear with P on opposite sides AND radii equal, so the arc-tangent directions at P coincide), bikar's per-edge-tag assignment becomes CONTAMINATED. The dominant lens's per-edge class tags appear majority but cross-class tags from the OTHER lens leak in (e.g., shape[0] has `[.lens_a×4, .lens_b×1]` instead of pure `[.lens_a×2]`). Co-tangent arcs at P interact with bikar's tangent comparator tie-breaking branch in a way that asymmetric-radius witnesses never triggered. The `type` field also degrades from `lens` → `unknown` (bikar's polygon-typer expects geometric asymmetry to classify a "lens"). **The bug lives at the per-edge-tag assignment path, NOT the face-walker's geometric correctness** — shape count is preserved, but downstream consumers that re-derive lens identity from source_primitives multisets (qiyas detector calibration, hierarchical diff matcher) will misclassify.

**Why:** qiyas#132 Tick 77 (2026-05-27) authored `dual-lens-shared-vertex-homogeneous.bkr.tmpl` as a controlled-comparison probe against Tick 23 (`dual-lens-shared-vertex.bkr.tmpl`, asymmetric radii 50/30/45 PASS clean). Tick 77 same topology, ALL three circles r=50 (CL_shared center=(58.3975,27.7350), CL_a=(127.7350,41.6025), CL_b=(72.2650,-41.6025), all r=50, all passing through P=(100,0)). CL_a + CL_b are ext-tangent at P (d=100=50+50, centers colinear with P on ±u_unit ray where u_unit = (1,1.5)/sqrt(3.25)). Expected: 5 shapes with disjoint per-lens source_primitives like Tick 23 (shape[0]=`[.lens_a×2, arc:#0, arc:#1]`, shape[1]=`[.lens_b×2, arc:#2, arc:#3]`). **ACTUAL: 5 shapes (count matches!) but source_primitives tangled**: shape[0]=`type=unknown, src=[.lens_a×4, .lens_b×1, arc:#0×2, arc:#1×2, arc:#2, layer:0×4]`; shape[1]=`type=unknown, src=[.lens_a×1, .lens_b×2, arc:#1, arc:#2, arc:#3, layer:0×3]`. The dominant lens's tags appear (lens_a dominates shape[0], lens_b dominates shape[1] — so an majority-vote classifier could still recover identity), but the contamination ratios are not 100%.

**Rule boundary refined (5-point spectrum, decoupling complete with Tick 79):**
- **Degree-4 all-arc shared vertex, ASYMMETRIC radii + tangents WELL-SEPARATED** (Tick 23): PASS both layers.
- **Degree-4 all-arc shared vertex, HOMOGENEOUS radii + tangents WELL-SEPARATED** (Tick 78): PASS both layers.
- **Degree-4 all-arc shared vertex, HOMOGENEOUS radii + CO-TANGENT** (Tick 77): PARTIAL (topology PASS, tags FAIL).
- **Degree-4 all-arc shared vertex, ASYMMETRIC radii + CO-TANGENT** (Tick 79, decisive decoupling probe): PARTIAL (topology PASS, tags FAIL) — IDENTICAL fingerprint to Tick 77 despite mass-asymmetric radii (r_a=30, r_b=70).
- **Degree-6 all-arc shared vertex, asymmetric radii** (Tick 75): FAIL both layers.

**Root cause sharply isolated (post-Tick-79): bikar's tangent comparator at degree-4 all-arc DCEL vertices consults ONLY tangent direction (mod 180°) for next-edge selection — it does NOT use radius/curvature as a tie-break secondary key.** When two non-shared arcs share the same tangent direction at the shared vertex (regardless of how asymmetric their radii are), the comparator's tie-break produces cross-class per-edge-tag contamination. Tick 78 (homogeneous + separated → PASS) and Tick 79 (asymmetric + co-tangent → PARTIAL) are orthogonal decoupling witnesses confirming this: tangent-direction is the only load-bearing variable; curvature is irrelevant. Tick 23's "fix" of using asymmetric radii works ONLY because it co-incidentally produced well-separated tangent angles, not because the comparator consults radii. The discriminator between Tick 77/79 PARTIAL and Tick 75 FAIL is *incidence degree* (4 vs 6).

**How to apply:** When authoring Tier 1 all-arc-vertex compositions, (a) **predict source_primitives contamination** when arc tangent directions at the shared vertex co-align (pairwise angular separation below the comparator's tie-break threshold — empirically below ~5°, while Tick 78's 20° minimum gap was sufficient for clean separation) — even if shape count is correct, source_primitives won't be pure; (b) when you NEED clean source_primitives at a multi-lens shared vertex with homogeneous radii, use **angularly distinct circle centers** (Tick 78 path — homogeneous radii but tangents well-separated produces IDENTICAL clean output to Tick 23 asymmetric-radius path); (c) the OLD heuristic "use asymmetric radii" is sufficient but no longer necessary — what matters is the tangent-direction layout at P; (d) for downstream consumers that re-derive identity from source_primitives, design them to handle dominant-tag majority voting rather than pure-tag equality matching, OR detect the co-tangent geometry upstream and route those cases differently; (e) when investigating "shape count correct but my downstream consumer says wrong lens", check the gt.json source_primitives for cross-class contamination — that's the Tick 77 fingerprint, and the diagnostic is to compute pairwise tangent-angle separation at the suspect vertex; (f) **the witness IS the limitation** — do NOT file as a bikar bug to chase unless someone implements a more robust comparator at all-arc vertices (the current behavior is correct topology + lossy tags when tangents co-align, which is graceful degradation, not crash). **This isolates per-edge-tag contamination from face-walker topology errors** — Tick 75 had BOTH defects compounding; Tick 77 has only the tag-layer defect.
